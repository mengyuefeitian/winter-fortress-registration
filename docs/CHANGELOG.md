# 版本开发记录

> 版本号统一在 `miniprogram/utils/version.js` 的 `APP_VERSION` 中管理。
> v1.4.0 起有 Git tag 可考；v1.1.0 / v1.2.0 当时未打 tag，日期为推算。

## 开发约定：版本号与提交规则

| 改动类型 | 版本位 | 示例 |
|---|---|---|
| 新增需求 / 功能变更 | 提升第二位，第三位归零 | `1.17.2` → `1.18.0` |
| 修 bug、纯视觉或文案微调 | 只提升第三位 | `1.17.2` → `1.17.3` |
| 架构级重构 / 不兼容变更 | 提升第一位 | `1.18.0` → `2.0.0` |

- **每次修改完成都必须提交一个 commit**（需求、bug 都一样），不要攒着一起提交。
- 一次会话里同时有新功能与 bug 修复，按最高档升第二位，CHANGELOG 里分小节写。
- 升版本号的动作链：`utils/version.js` → 本文件增小节 → `README.md` 版本历史加一行 → （官网已发布说明页时）`utils/updates.js` 的 `RELEASES` 顶部加一条 → 提交 → 合并 master → 打同名 tag。
- 纯文档 / 注释 / 工具脚本改动不改版本号，但仍需提交 commit。

## v1.18.27（修复「分区开通」批准报 ReferenceError + 静默失败后的幂等补完）

**现象**（用户 2026-10-27）：超管点「分区开通 → 批准」，开发工具报
`ReferenceError: normalizedCode is not defined @ autoRejectZoneCreation`，
手机上只显示半句「批准失败：can't find variable: n」（生产包变量名被压缩成 `n`）。

### 根因：一次「改一半」的批量重命名

`d0a0470`（分区编号放宽到 1-99999、统一用 `normalizeZoneCode`）把 `admin-review.js` 里的
`zoneCode` 批量替换成 `normalizedCode`，但 `autoRejectZoneCreation(applicationId, index, zoneCode, …)`
的**形参**没跟着改，函数体里却用了 `normalizedCode` → 只要走到这条分支就必崩。

⚠️ 这条分支**只在「分区编号已存在」时才走**，所以从 v1.18.8 一直潜伏到线上。
教训：**批量重命名必须连形参一起改**；改了变量名就顺手全局搜一遍旧名。

### 为什么会出现「编号已存在」

审批不是原子的。`createZone` 成功之后还有 `initAlliances → 改申请状态 → 改用户角色`，
而**客户端 `update` 存在「不抛错但没写进去」的静默失败**（项目里已多次踩到）。
于是会出现：分区已经建出来了，申请却还是 `pending`、用户还是 `user`；
超管再点一次「批准」→ 撞上「编号已存在」→ 走进上面那条崩溃分支。
所以用户看到的「批准失败」其实是**第二次尝试**的症状。

### 修法

1. **`autoRejectZoneCreation` 形参改名 `normalizedCode`**（与函数体一致），提示文案顺带说清
   「编号 X 已被「分区名」占用」，拒绝原因压到订阅消息 20 字上限内（`编号4130已被其他分区占用`）。
2. **「编号已存在」不再一律拒绝**：先判断这个分区是不是这位申请人自己的
   （`creatorId` / `adminIds` 命中）。是 → 说明上次批准已经建好了区，只是后续步骤没落库，
   **幂等补完**（置为 approved + 设为区管 + 通知），绝不把申请人的申请自动拒掉；
   不是 → 才是真撞号，自动拒绝。
3. 补完时若发现该分区联盟为空（当初死在 `initAlliances` 之前），补初始化一次 12 个联盟，
   不重复建区、不重复初始化。
4. **写后回读校验**：`commitZoneApproval()` 写完申请状态后用新增的
   `db.getAdminApplicationById()` 回读，仍是 `pending` 就抛「分区已建好，但申请状态未写入，
   请再点一次「批准」补完（不会重复建区）」—— 让超管知道该干嘛，而不是一句「批准失败」。
5. 新增 `db.getAdminApplicationById(applicationId)`（按 `_id` 单条读 `admins`）。

### 回归测试

`.workbuddy/tools/zone_approval_test.js`（17 条断言，mock db，改审批流程必须跑）：
撞别人编号→自动拒绝且不抛错、自己已建好的分区→补完不重复建区、联盟为空→补初始化、
正常建区、静默失败→可操作提示且保留待审核列表。

## v1.18.24（统计页联盟筛选 + 修复截图被裁切/被压扁）

### 1. 统计页没有联盟选项，却已被「第一个联盟」静默过滤

**现象**：区管 → 统计数据 → 数据统计，切到「兵工厂报名 / 峡谷报名」后没有联盟选框，
无法按联盟查看。

**根因**：这类截图的联盟筛选只在 WXML 里给「堡垒报名」渲染了选择器，而查询代码里写的是
`if (selectedAlliance) filter.allianceId = selectedAlliance._id`。`selectedAlliance` 在
`loadAlliances()` 里被默认设成 `alliances[0]` —— 于是兵工厂/峡谷 的统计**一直是只算第一个联盟**的，
界面上既看不到这个约束、也没有任何办法切换。总人数看起来「就是全分区的」，实际不是。

**修法**：联盟选择器对「堡垒 / 兵工厂 / 峡谷」三类都显示；兵工厂/峡谷 的列表头部补一个
**「全部联盟」**并默认选中（用一个哨兵 `_id = __all__`，**不能用空串** —— 选择器内部是
`wx:for wx:key="_id"`；查询时不加 `allianceId`，即看整个分区）；
堡垒报名保持原样（统计按联盟维度算，必须落到具体联盟）。区管页与超管全局统计页同步。

### 2. 保存截图：一次点击写两张图，一张被裁、一张被压扁

**现象**：保存兵工厂统计截图，得到两张都不对 —— 一张内容被截断（最后两行报名人员没了），
另一张完全模糊。实测两张图分别是 **750×1050** 与 **750×300**。

**根因（超管全局统计页 `superAdmin/all-statistics`）**：三个问题叠在一起。

1. 画布只在 `doSaveScreenshot` 开头创建一次，高度用 `buildScreenshotData()` ——
   而它只处理堡垒/官职，兵工厂/峡谷 落到 else 分支，返回 `Math.max(190, 300) = 300`。
2. 兵工厂/峡谷 分支里用 `canvas.height = totalHeight` 想改高度。**给已经创建的离屏画布
   赋 width/height 不会重新分配绘图缓冲**，内容仍按老尺寸被裁。
3. 兵工厂/峡谷 分支内部各导出一次（`destHeight = totalHeight`），而 if/else 链**末尾还有一次**
   全量导出（`destHeight = screenshotData.height` = 300）→ 同一次点击写两张图。

同时高度公式与绘制步进对不上：旧公式按「固定 50 + `ceil(总人数/3)`×40」估算，
实际绘制是「标签 30 + `ceil(分组成员/3)`×35」两段。用户那组数据（12 人 + 35 人）
旧公式算出 **1050**，实际需要 1120+ → 正好把最后两行裁掉；
压扁那张则是把 1050 高的画布按 destHeight=300 导出，纵向被压缩 **3.50 倍**
（用两张图的墨水条带做线性拟合，残差 < 0.5px，确认是同一幅绘制被压扁）。

**修法**：

- 新增 `measureActivityHeight(stats)`，高度与绘制步进一一对应，作为唯一真值来源；
  兵工厂/峡谷 改为**按该高度重建画布**再绘制（不再魔改已创建画布的 size）。
- 引入 `exportHeight`：各分支只负责「画好 + 设置 exportHeight」，
  **导出与保存统一收敛到函数末尾唯一一次**，`destHeight` 恒等于画布高度。
  这样「一次点击写多张图」「图片被拉伸/压缩」在结构上不再可能发生。

**新增测试**：

- `.workbuddy/tools/screenshot_height_test.js` —— 用用户坏图的真实数据复现，断言
  ① 一次保存只导出一次、只写一次相册 ② `destHeight ===` 画布高度 ③ 墨迹不越界且底部有余量；
  同时覆盖峡谷、行数取整边界、区管页防回归。修复后该组数据画布高度 = **1155**（旧 1050）。
- `.workbuddy/tools/statistics_alliance_test.js` —— 16 条断言覆盖三个类型的可选列表、
  「全部联盟」不带 `allianceId`、选具体联盟必须带 `_id`、切换类型要重建选中项。

## v1.18.23（修复区管无法删除自己创建的国战报名表）

**现象**：区管点「删除」删不掉自己刚创建的国战报名表，只提示「删除失败」，没有任何原因。

**根因：分区归属只认一条绑定来源，而区管有两条独立的上岗路径**

删国战配置走 `clearRegistrations` 云函数的 `deleteBattleConfig`，原校验只查 `admins` 集合：

```js
admins.where({ userId: openid, status: 'approved', zoneId })
```

但项目里「谁是某分区的区管」分散在**两处、且存的标识还不一样**：

| 来源 | 字段 | 存的值 |
|---|---|---|
| `admins` 区管/分区开通申请 | `userId` | **openid** |
| `zones` 分区本身 | `adminIds` / `creatorId` | **users 的 MongoDB `_id`** |

超管「添加区管」、批准区管时的 `updateZoneCreator` 只写 `zones.adminIds`；
只有走「区管申请」进来的才在 `admins` 里留记录。于是**只通过「添加区管」或
「分区开通」上岗的区管，在 `admins` 里查不到任何东西** → 判成「无权删除其他分区」。

**修法：四条来源任一命中即放行**（`canManageZoneFor`）

1. `admins` 已通过申请且 `zoneId` 匹配（`userId` 同时认 openid 与 Mongo `_id`）
2. `zones` 该分区的 `adminIds` / `creatorId` 含本人
3. `admins` 历史记录只有 `zoneName` 没有 `zoneId`（早期分区开通申请落库不完整）→ 按分区名兜底
4. 这张表就是本人创建的（`battleConfigs.creatorId` 存 openid）

同时**不再吞掉失败原因**：页面原来固定弹「删除失败」三个字，云端给的权限原因全部丢弃，
用户无从自助排查；现在用弹窗展示云端原文（例如提示去找超管确认分区绑定）。

**新增测试**：`.workbuddy/tools/battle_config_delete_test.js`，mock 云环境跑 8 个场景 ——
四种上岗路径均应放行、区管删别分区与普通用户必须拒绝、级联清理要删干净。

⚠️ **需重新上传部署 `clearRegistrations` 云函数**，否则修复不生效。

### 一、新增「本周通行证」

玩法：完成一次激励任务（约 30 秒）→ 解锁**自然周**（周一 00:00 – 周日 23:59:59，

（【激励1】`adunit-73c3d37e881de797`），插屏由流量主后台自带、代码不接。

`.workbuddy/memory/topics/features.md`「广告变现」一节。）

### 二、修复「点了没反应 / 不弹窗 / 控制台无报错」

**现象**：国战报名点提交没反应、非主游戏账号完全不能编辑、**弹窗一次都没出现**，
开发者工具 / 真机 / 体验版三端一致，**控制台没有任何报错**。

**根因（用户贴出的错误日志实证）**

```
showModal:fail confirmText length should not larger than 4 Chinese characters
```

`wx.showModal` 的 **`confirmText` / `cancelText` 最多 4 个中文字符**（或 8 个英文字母）。
本版写的是 `confirmText: '看视频解锁'` —— **5 个字，超了 1 个**，于是
**整个 `showModal` 调用直接走 `fail`，弹窗根本不显示**。

而旧代码 `fail` 分支是 `settle(false)`，等于把「弹窗失败」误判成「用户点取消」：

> 点击 → 弹窗创建失败（用户什么都看不见）→ 判定用户拒绝 → 操作被拦下

这就同时解释了四项症状：**不弹窗、不提交、不报错、三端一致**。

**修法**

1. **`confirmText` 改为 `去解锁`（3 字）**，顺手把 `cancelText` 从 `暂不使用`（4 字，贴边）
   改为 `暂不用`（3 字）留足余量。代码里已加醒目注释：**改这两个文案必须数字数**。
2. **`fail` 分支一律放行**（+ 写本地通行证 + toast）。用户什么都没看到的时候
   拒绝他，就是「点了没反应」；宁可少收这一次广告钱，也不能堵死功能。
3. **弹窗出现前的总闸 `PRE_MODAL_TIMEOUT = 12s`**：链路里能卡住的环节太多
   （云函数、storage、Promise 链、showModal 本身），逐个加超时必然漏分支。
   统一改成：只要弹窗还没交到用户手上，到点一定放行；弹窗一弹出就撤掉总闸，
   改由「弹窗超时 3 分钟」与「广告超时 90 秒」接管，避免用户正在看广告时被强行放行。
4. 弹窗前 `wx.hideLoading()`（去掉全局层冲突这一同类隐患）；
   用户点「暂不使用」时 toast 明确「本次操作未生效」，不再让他以为又卡住；
   链路每步加 `trace()` 日志，方便开发者工具里看卡在哪。

> **教训**：`showModal` 这类「参数不合法就整个 fail」的 API，失败时默认不打日志，
> 表现和「代码没执行」一模一样。以后遇到「点了没反应」，**先给所有 wx 调用的
> `fail` 回调加上 warn 日志**，比推理快得多。

**新增：超管「激励开关」页 → 链路自检**

真机没有控制台，光加日志解决不了问题。自检面板逐段探测并直接给出结论：

| 探测项 | 能定位什么 |
|---|---|
| 总开关 / 本周周期 / 本机通行证 | 本机是否已解锁（已解锁就不会再弹窗，属正常） |
| 远程开关（含耗时） | `appConfig/adGate` 读取是否失败、是否已回落默认值 |
| 云端通行证（含耗时） | `weekPass` 云函数是否可达；失败会直接放行，所以看不到弹窗 |
| 广告位 / 实例创建 / 素材加载 | 未开通流量主、广告位未生效、无填充、冷却期 |

结果下方给一句人话结论（先报硬错误、再报降级行为），可直接截图反馈。
`utils/ad.js` 新增 `probeAd()`（只 `load` 不 `show`，不打扰用户、不产生曝光）。

**新增：超管「激励开关」页 → 清除本机解锁状态（联调测试用）**

兜底逻辑会在多处「顺手」写本地通行证（云端查不到 / 弹窗失败 / 广告拉不到都放行并写本地），
导致**一旦失败过一次，本周之内再也弹不出解锁弹窗** —— 想复测只能等下周一。
按钮一次清掉三处，清一处都不够：

1. 本地 storage 通行证（`weekPassLocal`）
2. **云端 `users.weekPass`**（服务端权威记录；不清它，下一轮 `query` 仍判定已持有）

微信上下文，客户端伪造不了；用 `_.remove()` 而非写 `null`，避免 null→对象 的 -502001）。
**该 action 需要重新部署云函数才生效。**

**远程开关：不停机调整（掉量就关）**

线上生效值存在集合 `appConfig` 的一条文档里，字段：

```
{ registerGate: true, valueGate: true }
```

- `registerGate` 报名类；`valueGate` 增值类
- 改成 `false` → 客户端最长 **5 分钟内**全量生效（缓存 TTL），**不用发版、不用重新部署**
- 只认布尔值：写成字符串 `"false"` 会被忽略并回落默认，避免误配置
- 云函数是管理员权限读库，`appConfig` **不需要给客户端开任何权限**

⚠️ **不用手工建集合，也不需要考虑 `_id` 怎么填。** 读取逻辑是**自愈式**的，任一级命中即返回：

1. 按约定的 `_id = adGate` 取（云函数自动建的就是它）—— **但必须含开关字段才算数**
2. 否则扫描集合（前 50 条），取**第一条真正含开关字段**的记录（兼容手工建的随机 `_id`）
3. 一条带字段的都没有 → 建集合并写入默认开关；若已存在一条只有 `_id` 的**空壳**记录，
   则改用 `update` 给它**补上字段**（不走 `add`，否则同 `_id` 重复会报错）
4. 连写入都失败 → 用云函数内置的 `GATE_FALLBACK`，不影响用户正常使用

> ⚠️ **为什么要检查「含开关字段」**（踩过）：控制台手工添加记录时很容易**只填了 `_id` 就保存**，
> 留下一条空壳记录。若盲目信任 `_id = adGate` 就返回它，开关永远读不到值。
> 实测症状就是云端测试返回 `{"ok":true,"config":{"_id":"adGate"},"source":"remote"}` —— config 里只有一个 `_id`。

**字段值类型**：认 `true` / `false`，也认 `1` / `0`（控制台手工填值很容易填成数字）；
**字符串一律不认** —— `"false"` 会被当成真值用，是最危险的误配置，遇到会回落默认。
（遇到无效值时会顺手写回规范的布尔值，所以控制台里看到的值可能被纠正过。）

`source` 字段含义：`remote` 读到已有配置 / `repaired` 给空壳补了字段 / `created` 新建了默认文档 /
`cloudfunction` 用云函数内置兜底值。

**首次使用**：部署后在控制台跑一次云端测试（云函数 → `weekPass` → 云端测试 → 入参
`{"data":{"action":"config"}}`），集合和文档就会自动生成，之后改那两个布尔值即可。

> ⚠️ **`config` 分支必须放在 `openid` 校验之前**（踩过）：云端测试不携带 openid，
> 放在后面会被 `noOpenid` 直接拦掉，返回 `{"ok":false,"reason":"noOpenid"}`，
> 永远生成不出配置文档。小程序内调用有 openid，所以只有控制台测试会暴露这个坑。

**想在控制台手工建也行**（两种方式都可以，`_id` 写不写都不影响读取）：

- **JSON 模式**（推荐）：整体贴入，必须是合法 JSON——要有外层大括号、key 要加双引号
  ```json
  {"_id":"adGate","registerGate":true,"valueGate":true}
  ```
  少了大括号会报 `'key' 只能位于 '{' 或 ',' 之后`，这是 JSON 语法错误，不是平台限制。
- **默认模式**：用「添加字段」逐条加——`_id`（string，值 `adGate`）、
  `registerGate`（boolean）、`valueGate`（boolean）

想整站停摆（含提审期间）：改 `adConfig.js` 的 `ENABLED = false`，这个需要重新发版。
想在「集合完全不可用」时也能关：改云函数顶部的 `GATE_FALLBACK` 并重新部署云函数。

**超管可以在界面上直接改（推荐）**

入口：超管控制台 → 配置管理 → **激励开关**（`pages/superAdmin/ad-gate/ad-gate`）。
两个开关分别对应 `registerGate` / `valueGate`，改完点保存，本机立即生效、其他端最长 5 分钟。

鉴权是两层，缺一不可：

1. 页面层 `auth.isSuperAdmin(role)` —— 非超管踢回首页（只是体验层）
2. 云函数层 `setConfig` 再校验一次 `users.role === 'superAdmin'` —— **这才是真防线**，
   页面层能被绕过，云函数层绕不过

写入策略：先 `update` 约定文档 → 失败则建集合 + `add` → 再失败则更新集合第一条。
保存后会**回读一次**把真正生效值返回，界面按回读值刷新，避免「显示已关、实际没写进去」。

> **开关配置与「周」无关，配一次长期有效。** `registerGate` / `valueGate` 只是两个布尔值，
> 不会随周失效、不需要每周重配。每周变化的是**用户的通行证有效期**——本周日 23:59 到期、
> 周一 00:00 自动归零，用户需重新观看一次。页面上的「10月12日 - 10月18日」是按当前时间
> **动态计算**的展示文案（`getWeekRangeText()`），不是写死的日期；页面 `onShow` 会重算，
> 避免小程序挂后台跨过周一后显示陈旧。

> 因为通行证是「一次观看、本周全免」，拦截点铺得广并不会让用户反复看广告——
> 一周最多看一次。这也是敢于把管理员操作一并纳入的前提。

| 文件 | 职责 |
|---|---|
| `utils/adConfig.js` | 广告位 ID 与总开关（**必须替换为后台创建的真实 adUnitId**） |

**三条硬约束（改这些文件前必读）**

1. 小程序端激励视频是**页面内单例，不允许跨页面使用**（官方文档明确：小游戏端才是全局单例）→ 实例挂在页面 `this` 上，不做全局单例复用。
2. 奖励只在 `onClose` 且 `res.isEnded === true` 时发放——用户中途退出不发奖，这是平台合规强制项，不是可选项。

**两个已踩/将踩的坑**

- **云函数时区**：运行环境默认 UTC(+0)，自然周却要按北京时间算 → 先给时间戳 +8h 再交给 `Date` 方法处理（见 `beijingDate()`），否则周一/周日归属会整体错一天。
- **-502001 防御**：沿用 v1.18.13 的教训，`weekPass` 写入时若旧值是标量 `null`，先 `_.remove()` 再写对象，避免 MongoDB「不允许在标量上创建子字段」。

⚠️ **提审与合规风险（务必先看）**

微信审核对「不看广告就不能用功能」是有态度的。报名属于本小程序的**核心功能**，
强制观看广告才能报名，存在被判定「以广告阻断基础功能」而拒审或被用户投诉的风险。
因此：

- **提交审核前，先把 `registerGate` 改成 `false`**，过审后再远程打开——这是开关存在的最大理由。
- 广告拉不到时**一律放行**（已实现），保证任何情况下都不会真的把人堵死。
- 若收到官方警告或用户集中反馈，优先关 `registerGate`（报名），保留 `valueGate`（增值类），

## v1.18.13（游戏账号保存 -502001 真正根因：MongoDB 不允许在 null 上创建子字段）

**报错原文（真机）**
```
保存失败：document.update:fail -502001 database request fail.
[FailedOperation] multiple write errors:
[{write errors: [{Cannot create field 'kind' in element {bow: null}}]}, {<nil>}]
(-502001) [stage=accountUpdate] [id=74f7e2ce...]
```

**根因（v1.18.12 的推断被证伪，以此版为准）**

云数据库底层是 MongoDB，**不允许在标量上创建子字段**。账号里的 `furnace` / `barracks.shield|spear|bow` 在未设置时存的是 `null`，一旦要把它们从 `null` 改成 `{kind,value,stage}` 这样的**对象**，就被拒绝：

| 账号里的旧值 | 要写入的新值 | 结果 |
|---|---|---|
| `barracks.bow = null` | `{kind:'fire',value:8,stage:'T11'}` | ❌ `Cannot create field 'kind' in element {bow: null}` |
| `barracks.bow = {…}`（已是对象） | 新的 `{…}` | ✅ 覆盖已有字段，允许 |
| `barracks.bow = null` | `null` | ✅ 同类型，允许 |

熊坑报名建出的账号 `barracks` 三项全是 `null`、`furnace` 也是 `null`，所以**只有这类账号保存失败**；「信息完整」的账号这些字段本就是对象，从未出问题。
（同理，熊坑报名的 `syncFromRegistration` 回写 barracks 时也会撞上这个错，而它被 `.catch(() => {})` 静默吞掉——这正是「联盟一直没写进去」的元凶。）

> ⚠️ **勘误**：v1.18.12 曾推断根因是「主账号额外触发 `syncUserProfile`」，该推断**已由上述报错证伪**。v1.18.12 对 `syncUserProfile` 的降级改造本身无害（派生数据同步失败本就不该拖垮保存），予以保留。

**修法**
- 新增 `scalarToObjectPaths(oldDoc, patch, base)`：递归找出所有「旧值是标量（null）→ 新值是对象」的字段路径。
- 新增 `safeUpdate(id, oldDoc, patch)`：**先把这些路径整体 `_.remove()` 删除，再写入新对象**，绕过 MongoDB 限制。
- `save` 分支与 `syncFromRegistration` 分支的 update 全部改用 `safeUpdate`。
- 熊坑报名页补传联盟（v1.18.12 已做）现在才真正能落库——之前被这个 `-502001` 挡住了。

**验证**（5 个场景，含边界）：

| 场景 | 需先删除的路径 | 判定 |
|---|---|---|
| 熊坑账号：`furnace:null` + `barracks` 三项 null → 对象 | `furnace`, `barracks.shield`, `barracks.spear`, `barracks.bow` | ✅ |
| 部分填写：shield 已对象，spear/bow 仍 null → 对象 | `barracks.spear`, `barracks.bow` | ✅（说明**只填部分兵营也会失败**，不限于熊坑账号） |
| 对象 → null（降级清空） | 无 | ✅ 无误删 |
| 字段不存在 → 创建对象 | 无 | ✅ 无误删 |
| null → null | 无 | ✅ 无误删 |

## v1.18.6（熊坑分布图：文字不再依赖 textBaseline，昵称锚点用实测墨迹盒）

### 问题（用户升级 v1.18.5 后手机端反馈，配截图）
「熊坑的展示昵称**都不在对应的位置里面**，只有一个在里面，其余的都跑到外面的格子。」

### 根因（`utils/bearPitDraw.js`）
把手机截图按「8 个红旗子方块 + 熊坑」重新做了网格标定（U=80.4832 px/细格，8 点残差
< 0.02 细格），再逐点量三类文字相对各自锚点的墨迹位置，结论是：

| 文字 | 代码里的设置顺序 | 手机上实测偏移 |
|---|---|---|
| 熊坑白字「熊坑」 | `font` → `textBaseline='middle'` | 正常（middle 生效） |

正好在基线之上 0.35em，与实测值完全吻合，可确认该结论。昵称的 `ctx.font` 也是在

### 修法（彻底不碰 `textBaseline='middle'`）
- 新增 `setFont(ctx, fs, weight)`：**每次设置 `ctx.font` 之后立刻**重设

- 新增 `inkMetrics(ctx, text, fs)`：用 `measureText()` 量真实墨迹盒

## v1.18.5（熊坑分布图：昵称一定落在方格内、等级徽标统一贴右下角）

### 问题（用户手机端反馈，配截图）
「从手机端来看，**用户名称字体大小没有落在方格内**，同时，这个**数字标签统一放在方框
右下角展示**，目前在右上角不合适。」

### 根因（`utils/bearPitDraw.js` 的 `drawNickLabel`）
1. **昵称只按宽度缩字号**：`fitText` 只管「几行能放下」，不管**竖向**还装不装得下。
   而每个座位只有 2×2 细格，带等级的人还要把整体往下挪 `seat.h * 0.09` 给右上角
   徽标让位 —— 于是两行昵称（如「城南种田」「宇智波波斑」）的下沿正好压在格子
   底边上，手机上看就是「顶出方格」。
2. **徽标画在右上角**，和昵称第一行抢位置：5 个字的名字（如「狼堡你灰姨」）第一行
   会被深色胶囊盖掉半截。
3. 换行是纯贪婪的，4 个字会断成「城南种 / 田」这种尾行孤字，视觉上更像没排好。

### 修法（只改绘制层，**不动几何与排位算法**）
- `fitText` 新增 `maxH` 参数：缩字号同时受**宽度**和**可用高度**约束，两者都不满足才继续缩。
- `drawNickLabel` 改成**一个座位分两区**：昵称占上方（有徽标时就是「徽标上沿以上」那块），
  徽标占右下角。昵称区域的上下留白 7% / 6%，所以任何字数都不会再压到格边或压到徽标。
- 徽标统一 `x = 座位右 − 6% 宽 − 徽标宽`、`y = 座位下 − 6% 高 − 徽标高`；字号从
  `0.24 × 座位高` 收到 `0.22 ×`，横向内边距从 `0.14 × 座位宽` 收到 `0.12 ×`，
  位数多（会把胶囊撑过 64% 格宽）时自动再压一档字号。
- 新增**均衡换行** `balancedWrap`：先按行数把字数平均分（「城南种田」→ 城南 / 种田），
  分完超宽才退回贪婪断行。

### 验证
- 真机几何离线复现（393×852 CSS / dpr 3，无头 Chromium）：改前昵称下沿贴边、
  「902」压住「狼堡你」；改后 11 个人**全部完整落在格内**，最短边距 0.142 细格（座位高的 7%）。
- `bear_pit_test.js` 新增第 9 节：用假 ctx 把 `drawPit` 跑一遍，断言 140 个座位号 + 10 种

## v1.18.4（熊坑排位：改为「同环内自由换位」，保证邻居一定能挨上）

### 问题（用户反馈，配截图）
「这次修改的也不对，这个算法还是有问题。因为**到处混要求的邻居是小妖皮，但最后的结果却是
到处混和青衣放在邻居上了**。而**工藤和灰姨约定的邻居也没有做到**。到处混和灰姨在第二环，
就可以在二环任意位置，靠近他们的邻居进行安排互换位置，**同一环内可以互换位置**。
**为了保障需要相邻的两个人能够相邻**。」

### 根因（v1.18.3 的实现有两个死结）
1. **候选只从「已经有人坐的座位」里取**：`planSeats` 第 5 步只跟 `occ[seat]` 里已占座的人
   换位，**永远不会挪到空位**。而真实场景是 140 个位置才排 11 个人 —— 空位一大把，
   于是邻居修正**等于完全失效**。截图里「到处混」被卡在 11 号、「灰姨」卡在 9 号，
   离邻居（8 号 / 7 号）十万八千里，就是因为没有可用空位这个分支。
2. **`MAX_SWAP = 6` 的位移上限**：同环内稍远一点的座位（如 11 号 → 18 号，差 7）直接
   被判定为「跳太远不换」，于是只能放弃连坐。

### 修法（`utils/bearPitLayout.js` ↔ `cloudfunctions/bearPit/layout.js` 同步）
- **环的归属由名次决定、永不改变**（第 i 名 → 第 i 个可坐座位所在的环），
  因此「一环 1–8 号永远属于等级前 8 名」这条不会破。
- 第 5 步重写为「**同一环内自由换位**」（用户口径）：
  - 候选 = **本人所属环里、与目标座位相邻的座位**，空位就直接挪过去（旧的只换人不挪空位的死结解开）；
  - 座位有人时，允许与**同环、且不是自己/目标**的人互换（换完两人都还在本环）；
  - 移除了 `MAX_SWAP` 位移上限 —— 环内可以挪到任意位置；
  - 按「邻居链」处理：先算链深，**链尾先定、再一节节往回贴**（青衣→到处混→小妖皮 这种链能整条拉直）；
  - 只接受**不让「已连上邻居数」下降**的移动，避免反复横跳；最多迭代 24 轮。
- `LAYOUT_VERSION` 3 → 4：看板老数据在 `getBoard` 时自动重排一次并回写。

| 工藤新一 | 1102 | 7 号 | 7 号 |

一环 1–8 号仍然是等级前 8 名（空山拾签 ↔ 工藤新一 在环内互换了一格）。

### 需求要点（2026-10-09 与用户逐条确认）
- 首页新增「熊坑报名」入口，位置在**峡谷会战报名之后**，所有人可见。
- 报名页：联盟 + 昵称 + **地心探险等级**，二选一 **「按战力排」/「邻居」**。

### 座位模型（关键决策，改之前务必先读 `utils/bearPitLayout.js` 文件头注释）
- **方形同心环 6 环**：一环每边 3 个（含两个角）→ `4×3−4 = 8`；之后每环每边 +1 → **8 / 12 / 16 / 20 / 24 / 28 = 108 个座位**。

- 编号：**1 号在正下方，顺时针**（正下方 → 往左 → 左侧自下而上 → 顶部 → 右侧 → 回正下方）。
- 环半径按 **+1** 递进（一环 1.5，二环 2.5 …）。⚠️ 按 +0.5 递进会让相邻环四角座位重叠 0.25 格，实测 180 对冲突。
- 用户原话「多几个无所谓」，所以没有为凑 100 而破坏 8/12/16… 的规整递进。
- 座位边长恒为 1（固定大小）；外环座位少、边长长，空隙均匀分摊到同环相邻座位之间。

### 排位规则
1. **地心探险等级降序**占座；同等级按**报名时间**先到先得；1 号 = 全场最高等级。
2. **邻居**：可指定一位「已报名且未被别人选走」的人做邻居，尽量排到其相邻座位；A→B→C 这类链会整条拉直。
3. 相邻 = **共用边或斜对角**；同一环是一条**闭合回路**，起编位左右两侧也互为邻居（否则每环在 1 号处会断一个口子）。
4. **邻居目标被删除 / 被别人抢走 → 自动回落为「按战力排」**，`neighborNick` 一并清空，不留悬空指向。
5. 修正阶段只跟「无任何邻居关系」的人换位，不会破坏别人已绑好的邻居。
6. 重新提交（改等级 / 改昵称）会**重新排位**；普通用户不能取消，只有管理员能删。

### 实现要点
- **布局与算法是唯一来源**：`miniprogram/utils/bearPitLayout.js`（前端绘制）。
  `cloudfunctions/bearPit/layout.js` 是同一套代码的**手工副本**（云函数不能 require 小程序目录），
  由 `.workbuddy/tools/bear_pit_test.js` **逐座位比对 + 逐用例比对**，漂移直接失败。
- **一个联盟一个文档**（集合 `bearPitBoards`，`members[]` 数组整体读写）：
  一次重排 = 一次读 + 一次写，避免 100+ 次单行写把云函数拖死。
- 云函数 `bearPit`：`getBoard / register / remove / clearBoard`；
  容量上限 108（超出直接报「座位已满」）、昵称 24 字上限、重名覆盖、删人权限 `superAdmin / admin / auditor`（盟管仅本联盟）。
- 绘制 `utils/bearPitDraw.js`：编号 / 昵称两种模式，四象限配色（与用户给的第一张分布图一致），
  等级做成座位右上角小徽章，昵称最多两行并自动缩字号；邻居之间画红色虚线。
- 页面：`pages/user/bear-pit`（排位页）、`bear-pit-register`（报名）、`bear-pit-map`（全屏缩放图 + 保存到相册）。

### 部署注意
- 需在云开发控制台新建集合 **`bearPitBoards`**，并右键「上传并部署：云端安装依赖」部署新云函数 **`bearPit`**。

### 版本号
- `utils/version.js` 的 `APP_VERSION` → **1.18.0**（新增功能，升第二位、第三位归零）。

### 本轮修掉的问题（自测发现）
- 同环首尾（如 1 号与 8 号）原先判为不相邻 → 链条走到环末接不回来，已补「首尾相接」。
- 邻居目标失效后只清 `neighborSeat`、没回落 `mode` → 列表会显示一个并不存在的邻居，已改为 `resetNeighbor()` 一并回落为「按战力排」。
- 超员时算法会编出 109+ 的座位号 → 改为溢出者 `seatIndex = 0`（不占座），容量仍由云函数挡在写入前。

## v1.17.4（代码包静态资源瘦身，过「图片和音频资源」检测）

### 问题
微信「代码质量」检测项 **「图片和音频资源大小应不超过 200 K」未通过**。

### 判定口径（重要）
这条**不是**「单个文件不超过 200K」，而是**代码包内全部图片 + 音频资源的总大小不超过 200KB**。
（官方性能优化文档的措辞容易被读成单文件；社区里多个开发者实测 + 官方回复的口径都是「总和」。）
本包原先 **44 个 PNG + 5 个 SVG，合计 357.7KB**，超限 157.7KB，所以一直不通过。
音频资源本项目一个都没有（无 `wx.playBackgroundAudio` 之类），不用管。

### 瘦身策略（`.workbuddy/tools/optimize_images.py`）
1. **分辨率按实际显示尺寸倒推**：界面里 32px 显示的图标原本给的是 200×200 源图，
   改成 96×96（= 32px 的 3 倍屏，已到顶）；非正方形图按长边等比缩，不拉变形。
   game-account 的熔炉 / 兵营 / 火晶徽章最大显示 62px，**保留 120×120 不动**。
   头像最大显示 60px → 168×168；空状态插画会放大展示 → 144×144。
2. **PNG 调色板量化**：在 RMSE ≤ 8（肉眼在 32–62px 下不可辨）的前提下取最小色数。
   火晶这类带渐变的图从约 6900 色压到 128–256 色，体积降到 1/4。
3. 全部 PNG 用 `optimize + compress_level=9` 重写；透明通道以 `P + tRNS` 保留。
4. 顺手删掉 `miniprogram/` 下的 `.DS_Store`（本来就被 `packOptions.ignore` 排除，属卫生清理）。

### 结果
| | 之前 | 之后 |
|---|---|---|
| 最大单文件 | 22.6 KB | 5.6 KB |
| 资源总大小 | **357.7 KB** | **101.0 KB** |

**文件名与引用路径一个都没变**，所以代码零改动（`<image src>`、`ga.preloadBadges`、canvas 徽章绘制都不受影响）。

### 排查结论：会不会还有别的位置同样超标
- 全项目静态资源只有 `miniprogram/images/`（49 个），且**没有一个文件超过 200K**，
  唯一的问题就是总量。瘦身后留了约 99KB 余量，后续再加图标不容易再次触线。
- 另有 5 个**未被任何代码引用**的历史图标（`icon-battle` / `icon-check` / `icon-phone` /
  `icon-registration` / `icon-stats`，共约 4.9KB），本次**保留未删**（怕你后面还要用）；
  想彻底清干净的话删掉即可，删了也不影响任何功能。

## v1.17.3（修复国战报名「射手营等级」选不中）

### 现象

  真正的 `archerSpec` 从未被赋值，`archerView.has` 一直是 false。
  打开弹窗时同理读到 `bowSpec`（undefined），所以也不会回显既有值。

- `battle-registration.wxml`：射手营块的 `data-target` 改 **`archer`**（样式类 `lv-row-bow` 保留）。
- `battle-registration.js`：`TARGET_TITLES` 的 key `bow` → **`archer`**，并在两处加注释说明

- 新增回归测试 `.workbuddy/tools/battle_level_target_test.js`：校验 wxml 里每个 `data-target`

  - 未命中 → 回源并回写

## v1.14.0（外部链接改「复制链接打开」）

### 背景（重要 · 结论性）
小程序后台**没有「业务域名」入口 = 本小程序是个人主体**。微信官方规定：

> 「目前小程序内嵌网页能力暂不开放给个人类型账号和小游戏账号」

即个人主体**既不能配置业务域名，也不能使用 `web-view` 组件**，后台直接不给入口；且小程序**没有唤起系统浏览器的 API**（微信刻意不开放，防止外跳）。所以「点链接直接打开网页」在这个主体下**没有任何实现路径**，只能复制地址让用户去浏览器打开。

### 变更
- **外部链接统一走 `utils/link.js` 的 `openExternal()`**：复制链接 → `hideToast()` 掐掉系统提示 → 弹「…链接已复制，请粘贴到浏览器打开」（2.5s）。
  - 功能介绍各版本 → 「V1.7.0 说明链接已复制，请粘贴到浏览器打开」
  - 官网 → 「官网链接已复制…」；备案查询 → 「备案查询链接已复制…」
- **「关于」页官网 / 备案号右侧的 `›` 箭头改成「复制」标签**：点击行为就是复制，箭头会误导用户以为能站内打开。
- **功能介绍列表页顶部提示**改为「点击版本复制说明页链接，粘贴到浏览器即可查看」。
- **`pages/common/webview` 从 `app.json` 的 `pages` 中移除**（页面文件保留）：个人主体带着打不开的 web-view 页有审核风险。
  - 🔧 将来主体升级为企业/个体工商户并配好业务域名后，恢复两步：① 把该路径加回 `app.json`；② `utils/link.js` 的 `openExternal` 换成 `navigateTo` 该页。步骤已写进两处文件头注释。

### 说明
- 本轮**无云函数改动**，无需重新部署。
- 若不想让用户体验「复制 + 切浏览器」这一步，唯一出路是**升级为企业/个体工商户主体**（需营业执照 + 认证），配好业务域名后可恢复站内直开。

# 版本开发记录

> 版本号统一在 `miniprogram/utils/version.js` 的 `APP_VERSION` 中管理。
> v1.4.0 起有 Git tag 可考；v1.1.0 / v1.2.0 当时未打 tag，日期为推算。

## 开发约定：版本号与提交规则

| 改动类型 | 版本位 | 示例 |
|---|---|---|
| 新增需求 / 功能变更 | 提升第二位，第三位归零 | `1.17.2` → `1.18.0` |
| 修 bug、纯视觉或文案微调 | 只提升第三位 | `1.17.2` → `1.17.3` |
| 架构级重构 / 不兼容变更 | 提升第一位 | `1.18.0` → `2.0.0` |

- **每次修改完成都必须提交一个 commit**（需求、bug 都一样），不要攒着一起提交。
- 一次会话里同时有新功能与 bug 修复，按最高档升第二位，CHANGELOG 里分小节写。
- 升版本号的动作链：`utils/version.js` → 本文件增小节 → `README.md` 版本历史加一行 → （官网已发布说明页时）`utils/updates.js` 的 `RELEASES` 顶部加一条 → 提交 → 合并 master → 打同名 tag。
- 纯文档 / 注释 / 工具脚本改动不改版本号，但仍需提交 commit。

## v1.18.4（熊坑排位：改为「同环内自由换位」，保证邻居一定能挨上）

### 问题（用户反馈，配截图）
「这次修改的也不对，这个算法还是有问题。因为**到处混要求的邻居是小妖皮，但最后的结果却是
到处混和青衣放在邻居上了**。而**工藤和灰姨约定的邻居也没有做到**。到处混和灰姨在第二环，
就可以在二环任意位置，靠近他们的邻居进行安排互换位置，**同一环内可以互换位置**。
**为了保障需要相邻的两个人能够相邻**。」

### 根因（v1.18.3 的实现有两个死结）
1. **候选只从「已经有人坐的座位」里取**：`planSeats` 第 5 步只跟 `occ[seat]` 里已占座的人
   换位，**永远不会挪到空位**。而真实场景是 140 个位置才排 11 个人 —— 空位一大把，
   于是邻居修正**等于完全失效**。截图里「到处混」被卡在 11 号、「灰姨」卡在 9 号，
   离邻居（8 号 / 7 号）十万八千里，就是因为没有可用空位这个分支。
2. **`MAX_SWAP = 6` 的位移上限**：同环内稍远一点的座位（如 11 号 → 18 号，差 7）直接
   被判定为「跳太远不换」，于是只能放弃连坐。

### 修法（`utils/bearPitLayout.js` ↔ `cloudfunctions/bearPit/layout.js` 同步）
- **环的归属由名次决定、永不改变**（第 i 名 → 第 i 个可坐座位所在的环），
  因此「一环 1–8 号永远属于等级前 8 名」这条不会破。
- 第 5 步重写为「**同一环内自由换位**」（用户口径）：
  - 候选 = **本人所属环里、与目标座位相邻的座位**，空位就直接挪过去（旧的只换人不挪空位的死结解开）；
  - 座位有人时，允许与**同环、且不是自己/目标**的人互换（换完两人都还在本环）；
  - 移除了 `MAX_SWAP` 位移上限 —— 环内可以挪到任意位置；
  - 按「邻居链」处理：先算链深，**链尾先定、再一节节往回贴**（青衣→到处混→小妖皮 这种链能整条拉直）；
  - 只接受**不让「已连上邻居数」下降**的移动，避免反复横跳；最多迭代 24 轮。
- `LAYOUT_VERSION` 3 → 4：看板老数据在 `getBoard` 时自动重排一次并回写。

### 效果（用户截图那 11 人，邻居 4 条全连上）
| 昵称 | 地心 | 修复前 | 修复后 |
|---|---|---|---|
| 空山拾签 | 1056 | 6 号 · 邻5 | 6 号 · 邻5 ✅ |
| 工藤新一 | 1102 | 7 号 | 7 号 |
| 小妖皮 | 999 | 8 号 | 8 号 |
| **狼堡你灰姨** | 902 | 9 号（没挨到工藤新一） | **17 号 · 邻7** ✅ |
| **到处混** | 891 | 11 号（身边是青衣） | **18 号 · 邻8** ✅ |
| 青衣 | 981 | 10 号 · 邻11 | **19 号 · 邻18** ✅ |

一环 1–8 号仍然是等级前 8 名（空山拾签 ↔ 工藤新一 在环内互换了一格）。

### 注意
- ⚠️ **需要重新部署 `bearPit` 云函数** —— 座位号是云函数算的，前端只负责画。

## v1.18.3（熊坑排位再次修正：严格按名次落座 + 统一叫「地心探险」）

### 问题（用户反馈，配两张截图）
1. 「排位有问题」：**排名第一的跑到了 11 号位，排名最后的却占了 1 号位**；9、10 号位等级
   明显比 1 号位高，却被排在二环。
2. 「熊坑排位图手动输入的时候，默认还是会有最后一次输入的人名，还要手动删除才能输入。」
3. 「战力还是改成地心探险，在图中显示地心，统一采用用户能够理解的方式。」
4. 「排名人员列表，前面只需要有地心探险等级数字标记即可，不需要写战力，也不需要写地心。」

### 根因
`planSeats` 第 4 步把「整条邻居链挪到**链内排名最高者**的位置」，链里排名靠后的人
因此拿到很靠内的座位号；再加上第 6 步换位没有位移上限，出现「最后一名直接坐到 1 号位」。

### 修法（`utils/bearPitLayout.js` ↔ `cloudfunctions/bearPit/layout.js` 两份同步）
- **落座改成严格按名次**：删掉「整条链挪位」，第 i 名就坐第 i 个可坐座位。
- **换位只做本环内的就近修正**，并加三道闸：
  1. `|座位号差| ≤ MAX_SWAP`（6）——跳太远就放弃这次连坐，绝不长途搬运；
  2. `relationsHold` 只校验「**当前已经挨着**」的邻居关系（否则谁都换不动）；
  3. **更弱的人不许把「等级更高且本来更靠内」的人挤到外圈**（`rankPos[v] < rankPos[u]
     && v.ring < u.ring` 直接跳过）——这正是「最低等级坐到 1 号位」的病灶。
- 效果：一环 1–8 号**固定给地心等级前 8 名**；跨环的邻居（会让弱者进内环）宁可放弃连坐。
- `LAYOUT_VERSION` 2 → 3，云函数 `getBoard` 读老看板时自动重排一次并回写。

### 其它
- **报名表「手动输入」默认留空**：`components/account-nickname` 进入手动输入时
  不再把上一次的昵称带进输入框（用户每次都要先删干净）。
- **统一叫法**：全部界面去掉「战力」，改回「**地心探险**」；图上右下角标注
  「数字＝地心探险等级」；报名人员列表前面的徽标只留**数字**，不再带「战力 / 地心」二字。
- 座位脚注改为「按地心探险等级从高到低、由内圈往外排，1 号位在熊坑正下方」。

### 验证
- `bear_pit_test.js` 重写 7.11 / 新增 7.12（近邻换位）、7.13（用户截图那 11 人场景），
  全套断言通过；四件套 + 资源 101.3 KB / 200 KB 通过。

## v1.18.2（修正「熊坑排位」：严格按战力排，邻居只做就近换位）

### 问题（用户反馈）
「这个排序和排坑的时候，没有按战力排：优先按战力排，然后再调整相邻的位置。」
线上截图（战力第 4 的「小冬瓜」被挤到 **7 号**、战力第 7 的「到岸」却占着 **4 号**）——
只因为到岸选了「小妖皮」当邻居，座位号看起来完全不是战力名次。

### 根因
`planSeats` 的邻居修正阶段取的是 `neighborsOf(目标座位)[0]`，即**座位号最小**的那个候选，
谁坐在那儿就跟谁换。于是「7 号想挨着 5 号」跑去和 4 号换 → 低战力插队、高战力掉队。

### 修法（`utils/bearPitLayout.js` ↔ `cloudfunctions/bearPit/layout.js` 两份必须同步）
- 修正阶段改为**就近换位**：只跟「座位号离自己最近、且换完之后**不会拆散别人邻居**」的人换。
  用 `relationsHold()` 试算除自己以外的全部邻居关系，换完仍然成立才允许换。
- 效果：**座位号 ≈ 战力名次**。没选邻居的人最多挪 1 个名次；选邻居的人只挪到邻居旁边的座位。
  实测用户截图那 7 人：小冬瓜回到 **4 号**、到岸 **6 号 · 邻 5**、青衣 **7 号**。

### 看板自愈（`cloudfunctions/bearPit/index.js`）
- 看板文档新增 `layoutVersion`；`getBoard` 发现版本落后会**自动重排一次并回写**，
  历史数据不用让盟管重新报名。
- ⚠️ 必须重新部署 `bearPit` 云函数（右键「上传并部署：云端安装依赖」），否则线上还是旧座位号。

### 文案
- 熊坑相关界面统一写「**战力**」（报名表标签 / 提示 / 人员列表 / 图上说明）。
  数据字段仍是 `dixin`，与「我的 > 游戏账号」的「地心探险等级」是同一个数
  （用户口径：**战力就是地心探险等级**），所以只改叫法、没动字段。

### 验证
- `.workbuddy/tools/bear_pit_test.js` 新增 3 组用例（截图场景 / 无邻居时严格按名次 /
  远距离邻居时别人最多挪 1 名次），全套断言通过。
- 四件套 + 资源体积门禁 101.3 KB / 200 KB 通过。

## v1.18.0（新增「熊坑报名」：按等级自动排座 + 邻居连坐 + 排位图）

> ⚠️ **本节里的「座位模型」已被 v1.18.1 推翻**（108 座同心环 → 140 个位置风车形）。
> 排位规则、邻居连坐、存储与部署那几节仍然有效，座位几何以 v1.18.1 为准。

### 需求要点（2026-10-09 与用户逐条确认）
- 首页新增「熊坑报名」入口，位置在**峡谷会战报名之后**，所有人可见。
- 报名页：联盟 + 昵称 + **地心探险等级**，二选一 **「按战力排」/「邻居」**。
- 排位页：标题「熊坑」+ 已报名人数 + 报名按钮 + **熊坑分布图** + 报名人员表格。
- 每个**联盟一张图**，人数 = 该联盟当前报名人数；**不自动清空**，管理员可删人（删后自动重排）。
- 座位图可放大查看，并**保存到相册**。

### 座位模型（关键决策，改之前务必先读 `utils/bearPitLayout.js` 文件头注释）
- **方形同心环 6 环**：一环每边 3 个（含两个角）→ `4×3−4 = 8`；之后每环每边 +1 → **8 / 12 / 16 / 20 / 24 / 28 = 108 个座位**。
- **四角本身就是座位**，所以对角线不会出现用户吐槽的「一整片空位」。
- 编号：**1 号在正下方，顺时针**（正下方 → 往左 → 左侧自下而上 → 顶部 → 右侧 → 回正下方）。
- 环半径按 **+1** 递进（一环 1.5，二环 2.5 …）。⚠️ 按 +0.5 递进会让相邻环四角座位重叠 0.25 格，实测 180 对冲突。
- 用户原话「多几个无所谓」，所以没有为凑 100 而破坏 8/12/16… 的规整递进。
- 座位边长恒为 1（固定大小）；外环座位少、边长长，空隙均匀分摊到同环相邻座位之间。

### 排位规则
1. **地心探险等级降序**占座；同等级按**报名时间**先到先得；1 号 = 全场最高等级。
2. **邻居**：可指定一位「已报名且未被别人选走」的人做邻居，尽量排到其相邻座位；A→B→C 这类链会整条拉直。
3. 相邻 = **共用边或斜对角**；同一环是一条**闭合回路**，起编位左右两侧也互为邻居（否则每环在 1 号处会断一个口子）。
4. **邻居目标被删除 / 被别人抢走 → 自动回落为「按战力排」**，`neighborNick` 一并清空，不留悬空指向。
5. 修正阶段只跟「无任何邻居关系」的人换位，不会破坏别人已绑好的邻居。
6. 重新提交（改等级 / 改昵称）会**重新排位**；普通用户不能取消，只有管理员能删。

### 实现要点
- **布局与算法是唯一来源**：`miniprogram/utils/bearPitLayout.js`（前端绘制）。
  `cloudfunctions/bearPit/layout.js` 是同一套代码的**手工副本**（云函数不能 require 小程序目录），
  由 `.workbuddy/tools/bear_pit_test.js` **逐座位比对 + 逐用例比对**，漂移直接失败。
- **一个联盟一个文档**（集合 `bearPitBoards`，`members[]` 数组整体读写）：
  一次重排 = 一次读 + 一次写，避免 100+ 次单行写把云函数拖死。
- 云函数 `bearPit`：`getBoard / register / remove / clearBoard`；
  容量上限 108（超出直接报「座位已满」）、昵称 24 字上限、重名覆盖、删人权限 `superAdmin / admin / auditor`（盟管仅本联盟）。
- 绘制 `utils/bearPitDraw.js`：编号 / 昵称两种模式，四象限配色（与用户给的第一张分布图一致），
  等级做成座位右上角小徽章，昵称最多两行并自动缩字号；邻居之间画红色虚线。
- 页面：`pages/user/bear-pit`（排位页）、`bear-pit-register`（报名）、`bear-pit-map`（全屏缩放图 + 保存到相册）。

### 部署注意
- 需在云开发控制台新建集合 **`bearPitBoards`**，并右键「上传并部署：云端安装依赖」部署新云函数 **`bearPit`**。

### 版本号
- `utils/version.js` 的 `APP_VERSION` → **1.18.0**（新增功能，升第二位、第三位归零）。

### 本轮修掉的问题（自测发现）
- 同环首尾（如 1 号与 8 号）原先判为不相邻 → 链条走到环末接不回来，已补「首尾相接」。
- 邻居目标失效后只清 `neighborSeat`、没回落 `mode` → 列表会显示一个并不存在的邻居，已改为 `resetNeighbor()` 一并回落为「按战力排」。
- 超员时算法会编出 109+ 的座位号 → 改为溢出者 `seatIndex = 0`（不占座），容量仍由云函数挡在写入前。

## v1.17.4（代码包静态资源瘦身，过「图片和音频资源」检测）

### 问题
微信「代码质量」检测项 **「图片和音频资源大小应不超过 200 K」未通过**。

### 判定口径（重要）
这条**不是**「单个文件不超过 200K」，而是**代码包内全部图片 + 音频资源的总大小不超过 200KB**。
（官方性能优化文档的措辞容易被读成单文件；社区里多个开发者实测 + 官方回复的口径都是「总和」。）
本包原先 **44 个 PNG + 5 个 SVG，合计 357.7KB**，超限 157.7KB，所以一直不通过。
音频资源本项目一个都没有（无 `wx.playBackgroundAudio` 之类），不用管。

### 瘦身策略（`.workbuddy/tools/optimize_images.py`）
1. **分辨率按实际显示尺寸倒推**：界面里 32px 显示的图标原本给的是 200×200 源图，
   改成 96×96（= 32px 的 3 倍屏，已到顶）；非正方形图按长边等比缩，不拉变形。
   game-account 的熔炉 / 兵营 / 火晶徽章最大显示 62px，**保留 120×120 不动**。
   头像最大显示 60px → 168×168；空状态插画会放大展示 → 144×144。
2. **PNG 调色板量化**：在 RMSE ≤ 8（肉眼在 32–62px 下不可辨）的前提下取最小色数。
   火晶这类带渐变的图从约 6900 色压到 128–256 色，体积降到 1/4。
3. 全部 PNG 用 `optimize + compress_level=9` 重写；透明通道以 `P + tRNS` 保留。
4. 顺手删掉 `miniprogram/` 下的 `.DS_Store`（本来就被 `packOptions.ignore` 排除，属卫生清理）。

### 结果
| | 之前 | 之后 |
|---|---|---|
| 最大单文件 | 22.6 KB | 5.6 KB |
| 资源总大小 | **357.7 KB** | **101.0 KB** |

**文件名与引用路径一个都没变**，所以代码零改动（`<image src>`、`ga.preloadBadges`、canvas 徽章绘制都不受影响）。

### 排查结论：会不会还有别的位置同样超标
- 全项目静态资源只有 `miniprogram/images/`（49 个），且**没有一个文件超过 200K**，
  唯一的问题就是总量。瘦身后留了约 99KB 余量，后续再加图标不容易再次触线。
- 另有 5 个**未被任何代码引用**的历史图标（`icon-battle` / `icon-check` / `icon-phone` /
  `icon-registration` / `icon-stats`，共约 4.9KB），本次**保留未删**（怕你后面还要用）；
  想彻底清干净的话删掉即可，删了也不影响任何功能。

- `utils/version.js` 的 `APP_VERSION` → **1.17.4**（只做优化修复，升第三位）。

## v1.17.3（修复国战报名「射手营等级」选不中）

### 现象
国战报名 → 选日期 → 兵营等级 → **弓兵（射手营）**：选完等级点确定，格子里的值不更新；
盾兵、矛兵都正常。部分用户表现为「点了没反应」，并且因为提交校验要求三兵营齐全，
射手营恒为空时会卡在「请完整选择兵营等级（盾/矛/射）」，看上去像「无法选择」。

### 根因：`bow` 与 `archer` 两套命名混用
- 账号存储 / 报名记录里射手营的 key 是 **`bow`**（`gameAccounts.barracks.bow`、`battleRegistrations.barracks.bow`）。
- 但国战报名页的数据字段叫 **`archer`**（`archerSpec` / `archerView`，与 `ga.specsOf()` 返回的 `archerSpec` 对齐）。
- `openLevelSheet` / `onLevelConfirm` 都是用 `target + 'Spec'` 拼字段名，而
  `data-target="bow"`、`TARGET_TITLES` 的 key 也是 `bow` → 确认后写进了**不存在的 `bowSpec`**，
  真正的 `archerSpec` 从未被赋值，`archerView.has` 一直是 false。
  打开弹窗时同理读到 `bowSpec`（undefined），所以也不会回显既有值。

### 修法
- `battle-registration.wxml`：射手营块的 `data-target` 改 **`archer`**（样式类 `lv-row-bow` 保留）。
- `battle-registration.js`：`TARGET_TITLES` 的 key `bow` → **`archer`**，并在两处加注释说明
  「存储叫 bow、页面字段叫 archer，不是一个命名空间」。
- 新增回归测试 `.workbuddy/tools/battle_level_target_test.js`：校验 wxml 里每个 `data-target`
  都能对上页面字段，并模拟「点射手营 → 选火晶 8 + T12 → 确认」，断言 `archerSpec`/`archerView`
  被更新、`validate()` 不再被射手营卡住。

  - 命中但已过期 → 先用旧值，同时**后台静默回源**（stale-while-revalidate），同一 key 60 秒内只回源一次，避免连开多页打请求风暴
  - 写入类操作（建分区 / 改联盟名 / 绑盟管 / 初始化联盟 / 加区管）后自动 `invalidateMeta` 失效
  - 需要强制最新时传 `{ force: true }`
  - 实测：缓存命中 **0ms** 返回，无缓存时才会等网络（3s 模拟 → 3001ms）。
- 盟管控制台/区管控制台的联盟列表复用该缓存，不再各自写裸查询。

### 说明
- 本轮**无云函数改动**，无需重新部署。
- 新增全局样式 `.zone-readonly`（只读分区标签），各管理页统一使用，不要再写页内副本。

## v1.14.0（外部链接改「复制链接打开」）

### 背景（重要 · 结论性）
小程序后台**没有「业务域名」入口 = 本小程序是个人主体**。微信官方规定：

> 「目前小程序内嵌网页能力暂不开放给个人类型账号和小游戏账号」

即个人主体**既不能配置业务域名，也不能使用 `web-view` 组件**，后台直接不给入口；且小程序**没有唤起系统浏览器的 API**（微信刻意不开放，防止外跳）。所以「点链接直接打开网页」在这个主体下**没有任何实现路径**，只能复制地址让用户去浏览器打开。

### 变更
- **外部链接统一走 `utils/link.js` 的 `openExternal()`**：复制链接 → `hideToast()` 掐掉系统提示 → 弹「…链接已复制，请粘贴到浏览器打开」（2.5s）。
  - 功能介绍各版本 → 「V1.7.0 说明链接已复制，请粘贴到浏览器打开」
  - 官网 → 「官网链接已复制…」；备案查询 → 「备案查询链接已复制…」
- **「关于」页官网 / 备案号右侧的 `›` 箭头改成「复制」标签**：点击行为就是复制，箭头会误导用户以为能站内打开。
- **功能介绍列表页顶部提示**改为「点击版本复制说明页链接，粘贴到浏览器即可查看」。
- **`pages/common/webview` 从 `app.json` 的 `pages` 中移除**（页面文件保留）：个人主体带着打不开的 web-view 页有审核风险。
  - 🔧 将来主体升级为企业/个体工商户并配好业务域名后，恢复两步：① 把该路径加回 `app.json`；② `utils/link.js` 的 `openExternal` 换成 `navigateTo` 该页。步骤已写进两处文件头注释。

### 说明
- 本轮**无云函数改动**，无需重新部署。
- 若不想让用户体验「复制 + 切浏览器」这一步，唯一出路是**升级为企业/个体工商户主体**（需营业执照 + 认证），配好业务域名后可恢复站内直开。

## 数据库集合与权限

| 集合 | 说明 | 建议权限 |
|------|------|----------|
| `users` | 用户与角色 | 所有人可读写 |
| `superAdmins` | 超管手机号名单 | 仅创建者可读写 |
| `admins` | 区管 / 盟管 / 分区开通申请 | 所有人可读写 |
| `settings` | 全局配置（含自动清理） | 所有人可读 |
| `zones` | 分区 | 仅创建者可写，所有人可读 |
| `alliances` | 联盟 | 仅创建者可写，所有人可读 |
| `timeSlots` | 堡垒时间段 | 仅创建者可写，所有人可读 |
| `battleConfigs` / `arsenalConfigs` / `canyonConfigs` / `positionConfigs` | 各类活动配置 | 仅创建者可写，所有人可读 |
| `registrations` / `battleRegistrations` / `arsenalRegistrations` / `canyonRegistrations` / `positionRegistrations` | 各类报名记录 | 仅创建者可写，所有人可读 |
| `allianceMembers` | 联盟成员名单（跨周延续） | 通过云函数读写 |
| `allianceActivity` | 周活跃记录（仅保留本周） | 通过云函数读写 |
| `feedbacks` | 用户反馈与回复 | 通过云函数读写 |

> 联盟活跃相关读写全部收口到 `manageAllianceActivity` 云函数，绕开客户端 20 条查询上限与集合写权限限制。

## 定时清理

| 云函数 | 频率 | 职责 |
|--------|------|------|
| `clearRegistrations` | 每小时 | 按 `settings.autoClear` 清空报名数据；**每次运行都会清理联盟活跃过期周数据**（不受开关门控，跨天必须立刻清） |
| `cleanupApplications` | 每日 | 删除已处理超 14 天的审批记录（保留 pending） |

⚠️ **定时触发器按云函数独立注册，且开发者工具中不可见**，需到网页版云开发控制台确认。若触发器列表为空，函数不会自动运行——需重新部署或网页版手动添加。

## 更新版本号

修改 `miniprogram/utils/version.js` 中的 `APP_VERSION`：

```javascript
const APP_VERSION = '1.7.0'  // 更新此处
```

发版流程：改版本号 → dev 提交 → 合并 master → 推送两分支 → 打同名 tag（`v1.7.0`）。tag 号应与 `APP_VERSION` 保持一致。
